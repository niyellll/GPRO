# GPP Finance Pusat — one missing user on two-BASE Finance (NO-GO to cutover)

**19 November 2026 live read-only evidence:** Source legacy Supabase `vmpurwykfzcmculnnjfw.public.users` has 6 accounts and destination Finance BASE `fdhqidjltlihzdcbqfrd.gpp_piutang.users` has 5. Exactly **one source-only UUID** exists. All five shared UUIDs have matching stable username, password value, role and creation time. Differences for those five are only login session version and timestamps; they **must not be overwritten**.

The one source-only account has a nonempty credential and assigned role, is not admin/owner-like under a coarse role-name probe, and has no active session ID. Its identity, username, password and role must **never be pasted into tickets, GitHub, ChatGPT or CI logs**. It was created on 18 Nov and modified on 19 Nov; its role still needs independent owner authorization.

## Required steps (all seven source projects preserved)

1. **Before any --apply**, create encrypted backups of **all seven project PostgreSQL databases AND their physical private Storage objects**. Restore them into an isolated environment and demonstrate end-to-end recovery and rollback. This backup restore cannot be verified with migration tool arguments alone; obtain operator/owner-signed evidence.
2. Freeze GPP Pusat user/account creation, credential changes, and session lifecycle writes at the legacy source and named Finance BASE target. Obtain signed change ID and prove complete roster/count/stable SHA256 for *both* accounts tables from an authorized private PostgreSQL terminal.
3. Restrict both connection strings to private operator environment variables `GPRO_GPP_PUSAT_USER_SOURCE_DSN` and `GPRO_GPP_PUSAT_USER_TARGET_DSN`. TLS required; direct host uses `postgres` / 5432 and pooler identity `postgres.<exact-project-ref>` / 5432 or 6543. No Vercel `NEXT_PUBLIC_` variables, chat messages or GitHub secret uploads.
4. Obtain the missing account's approved **role** securely from the source (no username/UUID/password in shared artifacts). Have account owner confirm that migrated login must **reauthenticate**, and ensure changing the auth session version is understood. Require separate individual review if the role is privileged; this tool automatically refuses admin/owner-like roles.
5. Compute operator-only SHA256 for each snapshot with the same projection used by `stable_fingerprint_sql` in `ops/scripts/gpp_pusat_user_delta_guarded.py`: `id, username, password, role, created_at` serialized through `jsonb_build_object`, individual `sha256`, then concatenated digest ordered by UUID. Do not share these password-derived digests in public documents. The source must have exactly 6 rows and target exactly 5 at freeze time. The tool will independently recompute both SHA256 during execution.
6. Run the tool from the operator's isolated environment (psycopg3 required) without `--apply` for **read-only** rehearsal. Inspect aggregate result only. The tool rejects incorrect project/role/host, wrong passwords on existing IDs, duplicate usernames, extra target IDs or more than one missing source user.
7. Only if all above pass, invoke `--apply` with `--approved-change-ref`, `--verified-restore-ref`, `--confirm-frozen-writes`, `--confirm-session-reauthentication`, `--expected-source-rows 6`, `--expected-target-rows 5`, `--expected-source-sha256`, `--expected-target-sha256`, and `--expected-missing-role` (each filled from **fresh** private signoff).
8. Authorized apply takes an isolated read-only source snapshot and a serializable locked target transaction, verifies stable source/target fingerprints, **INSERTs ONLY the one source-only account**, preserving its credential and role and setting both active-session columns `NULL` while incrementing its `auth_session_version` by one. It then checks **six matching stable account identities**, five original target rows untouched, and final stable fingerprint equality before `COMMIT`. Any mismatch rolls back.
9. After staging, verify login for all six GPP Pusat users and denial for GPP Cabang/CSB/anonymous users, expiry/revocation semantics, application tenant boundary, password migration compatibility and all account-related operations. **Do not enable Preview or production two-BASE routing** merely because an account row was inserted. Retain five legacy Supabase projects until the full release gate passes.

## Risk notes

- This operation is a **single-account reconciliation**, not bulk password rotation or user migration. If a username, role or password changed during the freeze, **do not overwrite target**. Reconcile under owner approval.
- Login version increments invalidate only sessions **if the application actually enforces the session-version check**; verify that in E2E. A direct database copy is **not proof** of authentication compatibility.
- Existing five destination users keep their current auth session versions and active sessions unchanged. No session record is copied from legacy.
- The operator may run a dry-run while connected to a live database, but **no actual --apply has been run or approved** as part of this repository PR; backup/restore proof remains missing.
- This does **not** fix remaining CSB Finance 5 audit events, CSB Klarin six original private files (2,918,989 bytes), state v40→v38, five dedicated PostgreSQL tenant credentials or raw GPP Finance journal/piutang routes. Refer to `TWO_BASE_GO_LIVE_GATES_20261119.md` and issue #8.

**Decision:** NO-GO for final 7→2 cutover until all project data, private bytes, account login, rollback and full backup restoration are verified.
